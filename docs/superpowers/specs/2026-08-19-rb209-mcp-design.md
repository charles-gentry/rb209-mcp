# RB209 MCP Server + Skill — Design

**Date:** 2026-08-19
**Repo:** `charles-gentry/rb209-mcp` (public, `main`)
**Status:** Approved for planning

## Purpose

Provide a Model Context Protocol (MCP) server that exposes the AHDB RB209
(Nutrient Management Guide) Web API v2 to AI chat tools, plus a workflow skill
that guides the model through producing nutrient recommendations. Distribution
targets **non-technical users** via a one-click installer.

## Confirmed API facts (verified 2026-08-19)

- **Base URL:** `https://rb209api.ahdb.org.uk` (API v2). The v1 host
  `rb209-api-v1.ahdb.org.uk` is decommissioned 1 Apr 2027 — not targeted.
- **Spec:** public **Swagger 2.0** at `/swagger/v1/swagger.json` — 97 paths
  (89 GET, 8 POST), 102 `definitions`, 13 tags. Vendored into `spec/swagger.json`.
- **Auth (JWT):**
  - `POST /api/users/login` `{Email, Password}` → `{accessToken, refreshToken}`
    (access 60 min, refresh 30 days).
  - `POST /api/users/refresh_token` `{Email, RefreshToken}` → new tokens.
  - `POST /api/users/logout` (Bearer) invalidates the refresh token.
  - All data endpoints require `Authorization: Bearer <accessToken>`.
  - Login errors: `L03` account not verified, `L04` credentials invalid.
- **Rate limiting:** sliding window, 30000 req / 10 min, recalculated every 15s.
  Response headers `RateLimit-Limit/Policy/Remaining/Reset`; `429` on exceed.
  Trial licences also return `API-Trial-Licence-End-Date`.
- **Naming:** camelCase JSON (`soilTypeId`, `kReleasingClay`, `countryId`).
- **Central operation:** `POST /api/Recommendation/Recommendations` takes a deeply
  nested `DataInput` (Field → Arable/Grass/Grassland/Soil/OrganicMaterials/
  MannerOutputs/PreviousCropping + Nutrients flags) and returns `DataOutput`.

## Decisions (from brainstorming)

| Decision | Choice |
|----------|--------|
| Distribution | One-click `.mcpb` bundle now; core kept remote-ready for a hosted deployment later |
| Runtime | Node / TypeScript |
| Tool surface | Full 1:1 — every one of the 97 endpoints is its own tool |
| Skill | Workflow guide for building and reading recommendations |
| Credential model | Per-user: each user supplies their own AHDB RB209 login; credentials stay on their machine |

## Architecture

A single transport-agnostic core. At startup the server **loads the vendored
`swagger.json` and registers one MCP tool per operation** via a spec-to-tool
mapper, rather than 97 hand-written files. A single executor turns any tool call
into the correct HTTP request. This yields full 1:1 coverage with a small,
uniform codebase, and lets a remote (HTTP) entry point be added later without
changing tool logic.

### Components

- `src/openapi/loadSpec.ts` — read + parse the vendored spec.
- `src/openapi/resolveRef.ts` — resolve `#/definitions/...` `$ref`s (with cycle
  guarding).
- `src/openapi/toToolSchema.ts` — **pure function**: Swagger-2 operation →
  `{ name, description, inputSchema }`.
  - Name: `rb209_<tag>_<operation>`, snake_case, unique, ≤64 chars.
  - Path params → required properties; query params → optional; `in: body`
    `$ref` → resolved JSON Schema (nested objects/arrays).
  - Description: `summary` + parameter docs, kept terse.
- `src/http/authManager.ts` — lazy login; in-memory access-token cache; on `401`
  refresh via `refresh_token`, falling back to a fresh `login` if the refresh
  token is dead.
- `src/http/client.ts` — inject `Authorization: Bearer`; single retry on `401`
  after re-auth; parse `RateLimit-*`; map `429` to a clear "wait N seconds"
  error; surface `API-Trial-Licence-End-Date` at startup.
- `src/config.ts` — read `RB209_EMAIL`, `RB209_PASSWORD`, optional
  `RB209_ENABLED_GROUPS`, optional `RB209_BASE_URL` (default the v2 host).
- `src/server.ts` — build the MCP server, register generated tools, wire the
  executor.
- `src/index.ts` — stdio entry point for the bundle.

### Tool execution flow

1. Tool called with arguments validated against the generated input schema.
2. Executor looks up the operation, substitutes path params, appends query
   params, attaches the body (for POST).
3. `client.ts` performs the request with a valid bearer token, retrying once on
   `401`.
4. JSON response returned to the model; errors mapped to readable messages
   (`401` after retry, `429` rate limit, network failure, non-2xx body).

### Tool-count mitigation

97 tools is a large surface (some clients cap tool counts; it consumes context).
Mitigations: terse descriptions; the skill steers sequencing so the model need
not scan all tools; `RB209_ENABLED_GROUPS` (e.g. `Recommendation,Soil`) narrows
the set for constrained clients. Full set loads by default.

## Distribution: `.mcpb` bundle

- `manifest.json` declares the Node entry and two `user_config` fields — `email`
  (text) and `password` (sensitive) — so Claude Desktop renders a settings form;
  no JSON editing, no manual runtime install.
- `scripts/build-bundle.ts` esbuild-bundles the server and packages
  `rb209-mcp.mcpb`, attached to a GitHub Release.
- Install path: download → double-click → paste RB209 login. Credentials stay on
  the user's machine.
- Remote-ready: the core takes no dependency on stdio; a future HTTP entry can
  reuse `server.ts` unchanged.

## Skill

`skill/rb209-nutrient-planning/SKILL.md` — a workflow guide (standard skill
frontmatter + body). Teaches the model to:

1. Establish context via lookups (country, soil type, crop group → crop type,
   organic materials, previous cropping).
2. Assemble a valid `DataInput` (which fields matter for arable vs grass vs
   grassland; nutrient flags).
3. Call `rb209_recommendation_recommendations`.
4. Read the `DataOutput` — N/P/K/Mg/S/lime recommendations and any advice notes.

## Testing (red/green TDD)

- **Runtime:** TypeScript; **runner:** vitest; **HTTP mocking:** msw, driven by
  captured real fixtures in `test/fixtures/` (SoilTypes, Countries, Nutrients,
  CropGroups, OrganicMaterialCategories already captured; a real Recommendations
  response to be captured during implementation).
- Every unit written **red first**, then implemented to green:
  1. Swagger-2 → JSON-Schema mapping, including the deep `DataInput` (`$ref`
     resolution, nested arrays/objects, path/query/body params, tool naming).
  2. Tool-call → HTTP request mapping (path substitution, query string, body).
  3. AuthManager: login, token cache, `401` → refresh → re-login fallback.
  4. Error handling: `401` re-auth, `429` rate limit, network error, non-2xx.
  5. **Opt-in live integration test** against the real API, skipped unless
     `RB209_EMAIL`/`RB209_PASSWORD` are present in the environment.

## Out of scope (for now)

- Hosted/remote deployment and its per-user credential storage + OAuth-style flow
  (core is kept ready for it, but not built).
- Coverage of the decommissioned v1 API.
- Client-specific packaging beyond the `.mcpb` bundle (e.g. ChatGPT connectors).
